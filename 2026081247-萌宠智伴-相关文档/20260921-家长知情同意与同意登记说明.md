## 一、给家长看的《家长知情同意书》全文

> 以下文字与 `guardian_consent.py` 中的 `CONSENT_TERMS` 一致，前端可直接渲染，也可用于纸质《告家长书》排版。

**萌宠智伴 · 家长知情同意书**（版本 2026-09-v1，更新于 2026-09-21）

在孩子使用萌宠智伴之前，请您先了解我们会收集孩子的哪些信息、这些信息用来做什么、谁会看到、保存多久。除账号基本信息外，其余各项您都可以不同意；您也可以随时撤回同意。

一、我们收集哪些信息
孩子的姓名、学号、班级、头像；孩子与 AI 宠物的聊天内容和 AI 的回复、聊天时间；孩子自己记录的心情与学习情况。

二、这些信息用来做什么
让 AI 能接着上文与孩子对话；在孩子表达情绪低落、被欺负或学业压力时，让老师及时发现问题；用于本班教学情况统计。不用于任何商业用途，不对外提供。

三、谁可以看到
班主任在出现预警信号时可以看到相关对话内容；系统管理员进行内容合规检查；其他学生和家长看不到。每次查看都会留下记录，供学校核查。

四、保存多久
对话记录默认保存一个学年，到期后只保留不包含身份信息的统计数据，原文删除。

五、您可以不同意哪些内容
第 1 项账号基本信息是使用系统所必需的；第 2、3、4 项您可以每一项单独选择；第 5 项研究用途默认不勾选。如果不同意第 2 项，孩子的 AI 对话功能将暂停，课程学习、练习题、宠物养成等其它功能正常使用。

六、您和孩子的权利
可以随时撤回同意；可以查阅、复制孩子的信息；可以要求更正或删除；撤回或删除后，我们会停止相应的处理并删除对应数据。

七、我们的承诺
不把孩子的信息用于评优、处分等自动决策；不向第三方提供；不在公开场合展示孩子的聊天内容；如果使用目的、方式或信息种类发生变化，会重新征求您的同意。

如您对以上内容有疑问，请联系班主任或学校信息中心。

**监护人确认栏（纸质版）**：学生姓名＿＿＿＿ 班级＿＿＿＿ 监护人姓名＿＿＿＿ 与学生关系＿＿＿＿ 手机号＿＿＿＿ 签字＿＿＿＿ 日期＿＿＿＿

## 二、五个同意项

| 编号 | 同意项 | 说明 | 是否必需 | 不同意时的后果 |
|---|---|---|---|---|
| 1 | 账号基本信息 | 姓名、学号、班级、头像，用于登录与老师识别 | 必需 | 无法建立账号、无法使用系统 |
| 2 | 保存 AI 对话记录 | 保存孩子与 AI 的聊天内容与回复 | 可选 | AI 伙伴功能暂停，其它功能正常 |
| 3 | 情绪与困难关键词标记 | 对对话内容打"情绪低落/关系冲突/学业压力"标签 | 可选 | 不给该生打标，教师端预警不产生 |
| 4 | 教师查看与家校沟通 | 出现预警时班主任可查看相关对话并联系家长 | 可选 | 教师端看不到该生对话，无法介入 |
| 5 | 去标识化研究与模型改进 | 去掉身份标识后用于研究与模型迭代 | 可选（默认不勾） | 数据不进入研究/训练用途 |

规则：第 3、4 项依附于第 2 项，未同意第 2 项时会自动去除第 3、4 项。第 5 项必须单独勾选，默认不勾。

## 三、系统侧的可见性规则

| 场景 | 判定依据 | 未授权时的表现 |
|---|---|---|
| 学生发消息给 AI | 最新一条登记记录为已同意且含第 2 项 | 接口返回 403，提示家长未同意，不保存消息、不打标 |
| 教师端「对话查看」列表 | 含第 4 项 | 该生对话完全不出现 |
| 教师端「对话查看」详情 | 含第 2、4 项 | 返回 403，提示需联系家长本人或由班主任介入 |
| 管理员端「学生对话审核」 | 含第 2 项 | 该生对话不出现，审核操作也会被拒绝 |
| 管理员端「AI 使用总览」对话统计 | 含第 2 项 | 不计入统计 |

家长撤回同意后，以上所有入口立即失效，无需重启服务。

同意状态完全由 `guardian_consents` 表最新一条记录推导，不依赖任何冗余字段，因此不存在"两边状态不一致"的问题。

## 四、接口清单

| 接口 | 方法 | 可用角色 | 说明 |
|---|---|---|---|
| `/api/consent/terms` | GET | 无需登录 | 返回条款正文与五个同意项，家长可先看再决定 |
| `/api/consent/status` | GET | 学生本人/教师（本班）/管理员 | 返回某学生的同意状态、同意项、监护人信息（手机号已打码） |
| `/api/consent/send-code` | POST | 学生本人/教师（本班）/管理员 | 向监护人手机号发送验证码，60 秒内不可重复发送，有效期 10 分钟 |
| `/api/consent/submit` | POST | 同上 | 提交同意；短信方式需验证码，纸质方式需教师/管理员身份 |
| `/api/consent/revoke` | POST | 同上 | 撤回同意，新增一条 `status='revoked'` 记录 |
| `/api/consent/batch` | POST | 教师（本班）/管理员 | 按班级批量登记已回收的纸质同意书，已同意的自动跳过 |
| `/api/consent/list` | GET | 教师（本班）/管理员 | 登记明细与覆盖率汇总 |
| `/api/consent/classes` | GET | 教师/管理员 | 可选班级列表 |

提交同意请求示例：

```json
{
  "studentId": 12,
  "guardianName": "张三",
  "guardianRelation": "父亲",
  "guardianPhone": "13800001234",
  "code": "123456",
  "scopes": ["1", "2", "3", "4"]
}
```

## 五、数据库

`guardian_consents`：每次同意或撤回都**新增一条**，以该学生 id 最大的一条为准，历史记录不修改不删除，便于事后追溯。

| 字段 | 说明 |
|---|---|
| `student_id` | 学生 ID |
| `guardian_name` / `guardian_relation` / `guardian_phone` | 同意人与联系方式 |
| `scopes` | 同意项编号，逗号分隔，如 `1,2,3,4` |
| `terms_version` | 同意的条款版本，条款改动后旧记录保留旧版本号 |
| `status` | `agreed` 已同意 / `revoked` 已撤回 |
| `method` | `sms` 监护人短信确认 / `paper_batch` 纸质回收代登记 / `legacy_import` 历史存量 |
| `under_14` | 是否按不满十四周岁处理（小学各年级、初一、初二） |
| `operator_id` | 代登记的老师或管理员 ID |
| `consented_at` / `revoked_at` | 同意时间 / 撤回时间 |

`guardian_consent_codes`：监护人短信验证码，含 `used`、`expires_at`，建议定期清理一年前的记录。

## 六、部署与验证

1. 建表（服务启动时会自动建表，手工执行也可）：

   ```powershell
   mysql -uroot -p teacher_psych_system < database\20260921_guardian_consent.sql
   ```

2. 首次启用时，服务启动日志会打印：`[consent] 已启用家长知情同意机制，存量学生 N 人登记为历史存量`。
   存量学生按"学校已统一告知"处理，不会被突然切断对话功能，但应尽快回收纸质《告家长书》后重新登记。

3. 验证撤回效果（把 `2` 换成测试学生 ID）：

   ```sql
   INSERT INTO guardian_consents(student_id,guardian_name,guardian_relation,guardian_phone,scopes,
     terms_version,status,method,under_14,note,revoked_at)
   VALUES(2,'（演示撤回）','监护人','','','2026-09-v1','revoked','sms',0,'演示用撤回记录',NOW());
   ```

   执行后该学生在教师端「对话查看」中消失，发消息会收到家长未同意的提示。恢复方法见 SQL 文件第 4.4 节。

4. 纸质同意书批量登记：

   ```
   POST /api/consent/batch
   {"classId": 1, "scopes": ["1","2","3","4"], "note": "2026年秋季《告家长书》已回收"}
   ```

## 七、配置项（写在 `config_local.py` 或环境变量）

| 配置 | 默认 | 说明 |
|---|---|---|
| `CONSENT_ENFORCE` | `1` | 设为 `0` 时只记录同意情况、不做访问拦截，用于过渡期灰度 |
| `CONSENT_SMS_PROVIDER` | 空 | 留空时验证码直接返回给前端（开发模式），接入短信服务后填写服务商标识 |

## 八、上线建议

先说明一点：**本系统没有家长端**，家长不注册、不登录、不需要账号。家长只在两个环节出现：收纸质通知并签字，以及在孩子电脑前接收一条短信验证码。因此同意登记只可能落在已有的三个端上：

| 落地方式 | 在哪操作 | 需要的页面 | 接口 |
|---|---|---|---|
| 纸质《告家长书》回收登记（推荐，主用） | 教师端或管理员端 | 班级同意登记页（待做） | `POST /api/consent/batch` |
| 家长当场短信确认 | 学生端 | 同意书页面（待做） | `POST /api/consent/send-code` + `POST /api/consent/submit` |
| 查看登记覆盖率与明细 | 教师端或管理员端 | 登记情况页（待做） | `GET /api/consent/list` |

推荐的学校流程：统一发放纸质《告家长书》并回收，班主任在班级页面批量登记，系统保留登记人与时间；个别家长要求在系统内确认的，由学生在学生端打开同意书页面，家长输入手机号并输入收到的验证码。

注意：`CONSENT_SMS_PROVIDER` 为空时验证码会直接返回给前端（开发模式），此时"家长确认"这一环在技术上是不成立的，学生可以自己走完流程。正式使用必须接入短信通道，或者只走纸质登记。

## 九、本次改动范围之外

本次只做了同意机制本身。以下风险仍然存在，需要另行处理：

1. 后端 token 未做签名校验，角色字段可从请求头伪造，本模块的角色判断只能防误操作，不能防伪造。
2. 32 个 `/api/admin/*` 接口没有管理员角色校验，任意登录用户都能访问。
3. 教师密码明文存储、学生密码 MD5 无盐、管理员口令硬编码在代码中。
4. 教师查看对话尚未强制填写查看理由，留痕中也没有 IP 与理由字段。

建议优先完成第 1、2 项（加 `admin_required` 装饰器 + 签名 token），这两处不动数据库、不影响现有前端调用。
